One process snapshot per tick, and a slow one no longer ends a Codex session

Measured on this Mac: six Codex sessions' process trackers observing every half second for 5 seconds.

How often ps runs

Before: one snapshot per session
60 runs
After: one shared per tick
10 runs

Largest event-loop delay seen meanwhile: 55 ms before, 9 ms after. With six sessions the machine runs ps six times less often; the count no longer grows with the number of sessions.

A tracker that asks while a snapshot is already running waits for the next one instead of taking an older table, so ending a session's processes still sees everything up to its request.

Before, the first timed-out snapshot ended the Codex session. Now a busy machine just skips that observation; the first snapshot that establishes the session's ownership is retried the same way. Any other failure to inspect processes (a refusal, a missing root) still ends the session at once.
