Three lifetimes, and what happens after an Obeya crash

Workstream W3 of “Codex preview hardening, then Pi” · macOS 26 and a Linux ARM64 container · Claude Code 2.1.316, Codex CLI 0.162.0

Where the first two meet: an app that a Codex native terminal started is both. The shorter lifetime wins, so it ends with the session, app.keep or not. An app that must outlive its session would need a handoff Obeya does not have; this is stated, not solved. Claude workers record nothing, so for them the session ends nothing outside their own process group.

How the next start cleans up after a crash

  1. While a Codex session runs, the server holds a lease (a kernel file lock that dies with the process) and a record: the pid and creation time of the app-server and every descendant it observed, written before the app-server can run anything.
  2. The next Obeya on that home looks at each record only if it can take that record's lease. A live Obeya's records (another instance on the same directory, or its own) are busy and never touched.
  3. Records from an earlier boot are dropped unsignalled; other hosts, unreadable or unjudgeable records are left alone or quarantined and reported.
  4. Otherwise only the recorded processes whose pid still shows the recorded creation time are ended, with their descendants. Everything else is left alone. The record goes when none runs; if one survives, the record stays, the next start retries, and a new Codex session in that workspace refuses to start meanwhile (no second writer).

Limits to know

  • Cleanup, not containment: between the check and the signal a pid can be reused. On macOS the creation time has one-second resolution, so a wrong match needs the same pid reused in the same second the recorded process started.
  • An observation lost to a crash before it was written, and a child that detached unseen between two samples, are not recovered.
  • Windows records nothing; Claude Code and Pi record nothing yet.
  • Recovery results go to the server's log, not onto cards.
  • Parking still logs “the app keeps running” after Codex's tracker had ended the app; the new design chapter names this and does not resolve it.
