Platform process boundaries: what holds an agent's processes

A comparison of Obeya's current process tracking with two operating-system boundaries: a systemd user scope per session on Linux and a Job Object per session on Windows. Both were measured with a real Codex agent on real machines. Both are prototypes and are not yet used by Obeya.

LinuxDebian 13 (container), Ubuntu 22.04 and 24.04 (GitHub runners). Same results on all three.
WindowsWindows Server 2025 (GitHub runner), x64, nested inside the runner's own job.

A real Codex agent leaves four background jobs, then the session ends

Codex started four heartbeat processes. One stayed in its shell's process tree. Three detached into a process group of their own: the first one's launcher stays, the second's exits after 1.5 s, and the third's ("fast") exits at once. An unrelated process ran alongside and survived in every case.

The "fast" job's launcher exits before the tracker's first sample (every 500 ms), so nothing links the job to the agent any more. The weakness was known in theory and has now been observed on Linux and Windows.

What stays in, what gets out

  • Stays in, both platforms: a detached child, a new session or process group, a double fork, and on Windows start /b and a child created with the "break away from job" flag.
  • Gets out, Linux: asking systemd for a unit of its own (systemd-run), or moving itself to another cgroup the user owns.
  • Gets out, Windows: a process started through WMI. The task scheduler did start a task, but its process never reported back, so that way was not measured.
  • Nesting: Windows jobs nest correctly inside an outer job. On Linux a session's scope is a sibling of Obeya's own unit, so closing the terminal or stopping an Obeya service leaves sessions running until the next start ends them.

These boundaries hold against accidents, which is how processes have actually been lost so far. They do not hold an agent that deliberately tries to get out.

The app on a waiting card

Neither boundary ends anything on its own while Obeya runs. When the agent exits, its app keeps running inside the boundary. Parking's app.stop ends it as before, and an empty boundary disappears by itself.

Two decisions come before using this in Obeya.
  • For Claude workers, closing the boundary with the session would also end an app the worker started in a process group of its own. Codex already behaves this way today.
  • On Windows, the job ends session work every time Obeya exits, a graceful restart included. On Linux that work is ended at the next start instead.
