Process cleanup: what survives when Codex work stops

Measured on macOS with the installed Codex CLI 0.162.0 (no model turn), by running a real app-server through Obeya's transport. Each run starts three background heartbeats (same group as the shell; own session; own session whose launcher exits early) plus an unrelated canary process.

How it stopsHeartbeatsApp-serverUnrelated canary
Graceful closeall 3 stoppedgonealive
Forced closeall 3 stoppedgonealive
App-server killed (agent death)all 3 stoppedgonealive
Obeya itself killed (crash)all 3 keep runninggonealive

What this means

  • Cleanup comes from Obeya's own tracking of observed descendants; when Obeya crashes nothing runs it. Crash recovery is a later workstream.
  • app.keep only decides whether a waiting card's app is parked. It does not protect an app from shutdown: an app started as session work dies with its session, graceful or forced.
  • Fixed in this pass: one refused signal no longer spares the other processes (owed ones are retried); the app-server's group is signalled once at exit, not again by later timers; a failed Windows taskkill is reported instead of forgotten.

Limits

  • This is best-effort cleanup, not containment. Signalling by number still has a small reuse race, and a process that detaches between samples can escape.
  • Windows and native Linux Codex are unverified; macOS only. An earlier host-death probe saw a Codex-managed terminal stop; here the shell-started jobs kept running, so the result depends on how Codex started the process.
  • Full test suite: only the headless-browser skill tests fail intermittently here (unrelated to this change); everything else passes, and typecheck is clean.
